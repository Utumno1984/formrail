--- title: Async hydration without a false "modified" flag in a record editor date: 2026-11-27 slug: async-hydration-without-false-modified description: A record editor opens empty, the data arrives half a second later and the form claims unsaved changes. Why it happens, and two ways to avoid it with useObjectPageForm. author: Daniele Ingusci ---

You open a record in an editor. For half a second the fields are empty, then the data arrives and they fill in. You have not touched anything, yet the save bar slides in, and if you click "Back" the app asks whether you really want to discard your changes. It is a common small bug in record editors, and it erodes trust: a user who learns that the "unsaved changes" warning is sometimes wrong learns to ignore it, including the times it is right.

This article explains where the false "modified" flag comes from and shows two ways to avoid it with useObjectPageForm, the form-state hook of @formrail/core (MIT). The code blocks compile against the current public API of the package, and the behaviours described are covered by unit tests in the repository.

Where the false flag comes from

There are two independent causes, which often appear together.

Cause one: the form compares against the wrong thing

The simplest way to track "modified" is to remember the state the form started with and compare. If the form starts empty and the data is poured in afterwards, the comparison does exactly what it was told: the values differ from the empty initial state.

import { useEffect, useState } from 'react';

interface Invoice {
  customer: string;
  reference: string;
}

const EMPTY: Invoice = { customer: '', reference: '' };

// A stand-in for your data layer.
declare function fetchInvoice(id: string): Promise<Invoice>;

export function NaiveInvoiceEditor({ id }: { id: string }) {
  const [values, setValues] = useState<Invoice>(EMPTY);

  useEffect(() => {
    void fetchInvoice(id).then(setValues); // the data arrives: values now differ from EMPTY
  }, [id]);

  const isModified = values.customer !== EMPTY.customer || values.reference !== EMPTY.reference;
  return <p>{isModified ? 'Unsaved changes' : 'Saved'}</p>;
}

The flag is true as soon as the data arrives. The bug is not in the comparison but in the reference: the form should be compared with the record as it was last saved, and once the data has arrived, that is the record, not the empty placeholder shown while waiting.

Cause two: an echo that looks like a gesture

The second cause lives in the controls. A control may call its change handler when it is handed a new value from outside, not only when the user acts. If that handler marks the form as modified, the arrival of the data looks like the user typing. The same happens when a control normalizes what it receives (trims, reformats, rounds) and reports the normalized value back.

A control that never does this is a control without "echo". The controls of @formrail/core are built that way: changing value from outside never calls the change handler, only the user does. For Input you can watch it in the controlled story, whose play function sets a value from outside, checks that nothing was reported, then types and checks that the report arrives. Textarea, Select, Combobox, MultiSelect, NumberInput, DatePicker, Checkbox and Switch have unit tests for the same rule, all named "no echo". That is half of the answer. The other half is what the form does with the values it receives.

The flag is a comparison, not an event

useObjectPageForm takes a baseline, the last known saved state, and returns the current values and isDirty. The key design decision is that isDirty is a deep structural comparison of values against the real baseline, not a "touched" flag that something sets and something else has to clear. Two consequences, both tested:

  • Restoring the original value makes the form clean again: type a character, delete it, and isDirty is false again.
  • Setting a field to the identical value it already has (by Object.is) changes no value and, unless a save error is shown (every setValue clears it), does not re-render.

So a handler that fires "by mistake" with a value equal to the baseline is harmless. If a hydrated value equals the baseline there is nothing to explain; if it differs, the form is by definition modified, and the only way to avoid the false flag is to make the baseline the hydrated record. The two options below do that.

By default, equality is strict: '', null and undefined are all different from each other, and a key set to undefined differs from a missing key. Dates compare by time, plain objects and arrays by content.

Option one: mount the editor already hydrated

The most robust fix is to avoid the problem. Do not render the editor until the record exists, and give useObjectPageForm the record as its baseline at mount. There is no empty state to leave and nothing to reset. While the record is in flight, the page shows a loading state with no editable field.

import { useEffect, useState } from 'react';
import { Field, Input, useObjectPageForm } from '@formrail/core';

interface Invoice {
  id: string;
  customer: string;
  reference: string;
}

declare function fetchInvoice(id: string): Promise<Invoice>;

function InvoiceEditor({ invoice }: { invoice: Invoice }) {
  // Read once, at mount: the record is the baseline, so `isDirty` is false until the user edits.
  const form = useObjectPageForm({ baseline: invoice });
  return (
    <form>
      <Field label="Customer" name="customer">
        <Input value={form.values.customer} onChange={(event) => form.setValue('customer', event.target.value)} />
      </Field>
      <Field label="Reference" name="reference">
        <Input value={form.values.reference} onChange={(event) => form.setValue('reference', event.target.value)} />
      </Field>
      <p>{form.isDirty ? 'Unsaved changes' : 'Saved'}</p>
    </form>
  );
}

export function InvoicePage({ id }: { id: string }) {
  const [loaded, setLoaded] = useState<Invoice | null>(null);

  useEffect(() => {
    let ignore = false;
    void fetchInvoice(id).then((invoice) => {
      if (!ignore) setLoaded(invoice);
    });
    return () => {
      ignore = true; // a response for an `id` we have already left is discarded
    };
  }, [id]);

  if (loaded === null || loaded.id !== id) return <p role="status">Loading invoice…</p>;
  // `key`: another record is another editor, mounted hydrated, never a reset of the old one.
  return <InvoiceEditor key={loaded.id} invoice={loaded} />;
}

Three details do the work. The editor is a separate component, so the hook runs only once the record is available. The key makes a different record a different editor, with its own baseline. And the loaded.id !== id check keeps the old record off the screen while the new one loads.

This is the pattern of the worked example in Storybook. Open the sales order page, slow the load with the loadDelayMs control, and you see a loading state with no field, then the editor with the save bar hidden. Its play function changes a quantity (the bar appears) and puts the old one back (the bar goes away).

Option two: hydrate an existing form with reset

Sometimes the form has to exist before the data does: a page shell owns it, or one component handles both creation and editing. For that case the hook offers reset(newBaseline). It replaces the baseline and the values at once, so the form is clean afterwards, and it is the explicit way to say "this is the saved state now" rather than an edit by the user. The hook has no change callback at all: nothing is reported to you when you hydrate it.

import { useEffect, useState } from 'react';
import { Field, Input, useObjectPageForm } from '@formrail/core';

interface Invoice {
  customer: string;
  reference: string;
}

// Module-level and stable: the `baseline` option is read once, at mount.
const EMPTY: Invoice = { customer: '', reference: '' };

declare function fetchInvoice(id: string): Promise<Invoice>;

export function InvoicePage({ id }: { id: string }) {
  const form = useObjectPageForm({ baseline: EMPTY });
  const { reset } = form; // `reset` keeps its identity across renders
  const [loadedId, setLoadedId] = useState<string | null>(null); // the record the form holds
  const loading = loadedId !== id;

  useEffect(() => {
    let ignore = false;
    void fetchInvoice(id).then((invoice) => {
      if (ignore) return;
      reset(invoice); // baseline and values become the record; `isDirty` is false
      setLoadedId(id);
    });
    return () => {
      ignore = true;
      setLoadedId(null); // disabled until the next record is in the form
    };
  }, [id, reset]);

  return (
    <form>
      <Field label="Customer" name="customer">
        <Input
          disabled={loading}
          value={form.values.customer}
          onChange={(event) => form.setValue('customer', event.target.value)}
        />
      </Field>
      <p>{form.isDirty ? 'Unsaved changes' : 'Saved'}</p>
    </form>
  );
}

There are three traps, each a consequence of how the hook is specified.

The baseline option is not a subscription. It is read once, at mount. Passing a different baseline later changes neither values nor baseline, and in development the hook logs a single warning pointing to reset(newBaseline). That is why the example passes a stable constant and hydrates through reset. An inline literal with the same content does not warn.

A late reset discards edits. It replaces the values, so anything typed between the first render and the arrival of the data is gone. This is the strongest argument for option one, and the reason the example keeps the control disabled until the record arrives, and again while any later one loads: the cleanup clears loadedId, so a record about to be replaced cannot be edited. If the user can type before hydration, you have a product decision to make, not a library detail.

Responses can arrive out of order. Without the ignore flag, a slow response for the previous record could call reset after the current one and overwrite it.

What StrictMode does, and what it does not

In development, StrictMode runs one extra setup-and-cleanup cycle of every effect when a component first mounts (a simulated unmount and remount; state is kept). For the code above this has one visible consequence: fetchInvoice is called twice, and the response of the first call is dropped by the ignore flag, because its cleanup ran before it arrived. Only the second response reaches setLoaded or reset.

It does not change the dirty state: in both options the form is clean after the data has arrived, with StrictMode as without. Both are tests in the repository (use-object-page-form.async-hydration.test.tsx), run with the real Input and a deferred promise standing in for the network. In production there is no extra cycle, so the second request disappears.

When a control rewrites what it receives

If a control from another library normalizes its value and reports it, your handler receives a value that differs from the baseline and the form is dirty, correctly, by its own definition. Two remedies, in order of preference. First, normalize the data once when it arrives and use the normalized record as the baseline: the echo then equals the baseline and, as seen above, is harmless. Second, tell the form what "equal" means with the isEqual option, which replaces the comparison behind isDirty:

import { useObjectPageForm } from '@formrail/core';

interface Invoice {
  customer: string;
  reference: string;
}

export function useInvoiceForm(invoice: Invoice) {
  return useObjectPageForm({
    baseline: invoice,
    // A reference is the same reference whatever its case or surrounding spaces.
    isEqual: (a, b) => a.customer === b.customer && a.reference.trim().toUpperCase() === b.reference.trim().toUpperCase(),
  });
}

Use the second remedy sparingly: isEqual decides isDirty (and whether a changed baseline option warns), and the values still hold whatever the control reported.

If you use another form library

Everything above is about useObjectPageForm. If your forms are built with React Hook Form or TanStack Form, Formrail Pro, the commercial part of the project, has adapters for both, so that its Change Summary and Form Rebase engines work on those forms. They solve a different problem (showing what changed against the saved baseline, and reconciling edits when the record changes on the server). The principle carries over: whatever "unmodified" is compared against must be the saved record, not the placeholder shown while it loaded.

The checklist

  • Compare with the baseline, not with a touched flag.
  • Prefer mounting the editor already hydrated, keyed by the record id.
  • If the form must exist first, hydrate with reset(record), disable the controls until then and drop out-of-order responses.
  • For controls that echo, normalize the baseline or give the form an isEqual.
  • Test with StrictMode on.
